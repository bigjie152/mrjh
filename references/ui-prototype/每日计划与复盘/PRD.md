# 每日计划与复盘 PRD

## 1. 背景

用户希望开发一个个人自用的每日计划表小应用，参考《认知觉醒》中“计划完成”和“实际完成”左右对照的每日计划表。应用的核心价值是记录每天原本的时间安排与真实完成情况之间的差异，长期积累后帮助用户提升时间预估能力、计划能力和复盘质量。

当前已有一版前端 UI 原型，用户认可它的整体风格。后续开发应尽量复用现有页面风格和交互结构，把重点放在中文友好、操作流畅、本地优先、可部署到 Cloudflare Pages。

## 2. 产品目标

### 2.1 核心目标

帮助用户每天完成三件事：

1. 早上写下今日核心事项和计划时间块。
2. 晚上补充真实发生的时间块。
3. 自动看到计划与实际之间的偏差，并写下复盘。

### 2.2 长期目标

- 让用户逐步校准“我做一件事到底需要多久”的判断。
- 帮助用户识别常见偏差来源，例如低估耗时、临时事务、状态波动、拖延、心流延长。
- 形成可搜索、可导出、可回顾的个人时间复盘档案。
- 在网页端稳定使用，并支持 Cloudflare Pages 长期部署。

## 3. 目标用户

### 3.1 主要用户

个人使用者，偏向自我管理、学习、写作、工作复盘、时间记录场景。

### 3.2 使用场景

- 早上规划一天。
- 白天快速补记实际发生的事项。
- 晚上复盘计划和实际差异。
- 周末查看历史记录，寻找常见偏差模式。
- 导出当天记录为图片，用于归档或分享给自己。

## 4. 产品原则

### 4.1 全中文友好

- 页面主要文案使用中文。
- 按钮、表单、空状态、错误提示、确认提示、导出文件名都应自然、明确。
- 保留少量英文装饰字样时，不能影响理解。
- 避免残留 AI Studio、Google、Gemini 等与当前产品无关的模板文案。

### 4.2 操作流畅

- 高频动作应少点击、少打断。
- 添加时间块后自动回到当前上下文。
- 复制计划到实际记录应支持单条复制和批量复制。
- 弹窗、表单、编辑态要轻快，避免大面积阻塞。
- 输入过程中不应卡顿，数据保存不能明显打断操作。

### 4.3 本地优先

- 默认不需要账号。
- 默认不需要后端服务。
- 数据优先保存在用户浏览器本地。
- 后续增加云同步时，也应保留本地离线可用能力。

### 4.4 保留现有视觉方向

- 纸张感、手帐感、温润配色可以继续沿用。
- 左右对照是主页面的视觉中心。
- 页面看起来要像“可长期写的工具”，避免太营销化。

## 5. 功能范围

### 5.1 MVP 必须支持

#### 今日对照

- 选择日期。
- 自动显示星期。
- 创建和编辑 1-6 个核心待办。
- 勾选待办完成状态。
- 添加计划时间块。
- 添加实际时间块。
- 时间块支持开始时间、结束时间、内容、分类、关联待办。
- 实际时间块支持填写偏差原因。
- 支持从计划时间块复制到实际时间块。
- 支持一键复制全部计划为实际记录。
- 自动计算单个时间块耗时。
- 自动计算计划总时长、实际总时长、差额。
- 支持每日复盘字段：最大偏差、明日改进、随笔备注。

#### 历史归档

- 按日期查看历史记录。
- 支持搜索任务、计划、实际记录、复盘文字。
- 支持选择某一天回到今日页编辑。
- 支持复用某天的任务和计划为当前日期模板。
- 支持删除某天记录，并有明确确认。

#### 偏差统计

- 展示连续记录天数。
- 展示总任务完成率。
- 展示累计实际记录时长。
- 展示平均时间掌控度。
- 展示最近 7 天趋势。
- 展示分类计划与实际投入对比。

#### 导出

- 支持导出当前日期为 PNG 长图。
- 导出文件名包含日期。
- 导出内容应优先保证中文可读、布局完整。

### 5.2 第一阶段增强

- 日期默认使用真实当天。
- 修复所有模板残留英文和不自然中文。
- 清理不使用的依赖。
- 增加数据导出 JSON。
- 增加数据导入 JSON。
- 增加清空全部本地数据入口，并要求二次确认。
- 优化移动端布局。
- 优化表单校验，例如结束时间早于开始时间时明确提示跨天或错误。
- 替换浏览器 `alert` / `confirm` 为统一的中文轻提示和确认弹层。

### 5.3 第二阶段增强

- IndexedDB 存储。
- 数据版本迁移。
- PWA 离线缓存和桌面安装。
- 自定义分类。
- 常用时间块模板。
- 快捷键。
- 周报和月报。
- Cloudflare D1 / KV 云同步可选方案。

## 6. 页面设计

### 6.1 今日对照页

目标：完成一天的记录闭环。

页面结构：

```text
顶部导航
日期控制区
核心待办清单
计划完成 / 实际完成双栏
总结与认知校准
```

关键交互：

- 修改日期后切换到对应记录。
- 没有对应日期记录时，先展示空白模板。
- 填写任意内容后自动创建该日期记录。
- 单条计划可以复制到实际记录。
- 实际记录与计划匹配后展示偏差标签。

### 6.2 历史归档页

目标：快速找回、复用和整理过往记录。

页面结构：

```text
搜索框
历史卡片列表
每张卡片展示日期、星期、任务完成率、预计/实际时长、匹配率、核心任务摘要
```

关键交互：

- 搜索结果即时过滤。
- 点击“去修改此日”进入今日页并切换日期。
- 点击“复用为拟安排”把历史任务和计划复制到当前日期。
- 删除前明确提示日期和不可恢复风险。

### 6.3 偏差统计页

目标：让用户看到长期趋势。

页面结构：

```text
指标卡片
最近趋势图
分类投入对比
复盘摘录
```

指标说明：

- 连续记录天数：今天或昨天有记录时继续计算。
- 总任务完成率：已填写任务中完成任务占比。
- 累计记录时长：所有实际时间块总和。
- 平均时间掌控度：计划和实际在分类维度上的重合程度。

## 7. 数据模型

### 7.1 DailyPlannerEntry

```ts
interface DailyPlannerEntry {
  date: string;
  weekDay: string;
  tasks: TaskItem[];
  plannedBlocks: PlannedBlock[];
  actualBlocks: ActualBlock[];
  review: DailyReview;
}
```

### 7.2 TaskItem

```ts
interface TaskItem {
  id: number;
  text: string;
  completed: boolean;
  notes?: string;
}
```

### 7.3 PlannedBlock

```ts
interface PlannedBlock {
  id: string;
  startTime: string;
  endTime: string;
  taskRef: number | null;
  content: string;
  category: CategoryType;
  estimatedMinutes: number;
}
```

### 7.4 ActualBlock

```ts
interface ActualBlock {
  id: string;
  startTime: string;
  endTime: string;
  taskRef: number | null;
  content: string;
  category: CategoryType;
  actualMinutes: number;
  reason?: string;
}
```

### 7.5 DailyReview

```ts
interface DailyReview {
  biggestDeviation: string;
  improvement: string;
  generalNotes: string;
}
```

## 8. 核心计算规则

### 8.1 时间块耗时

- 输入开始时间和结束时间。
- 同一天内：结束时间减开始时间。
- 跨天时：按 24 小时补足计算。
- 第一阶段需明确 UI 提示，避免用户误填造成异常大耗时。

### 8.2 单条偏差

实际记录匹配计划记录的优先规则：

1. taskRef 相同。
2. 内容完全相同。
3. 后续可增加模糊匹配。

偏差类型：

- 完美重合：实际耗时等于计划耗时。
- 超时：实际耗时大于计划耗时。
- 缩短：实际耗时小于计划耗时。
- 新增记录：找不到对应计划。

### 8.3 时间掌控度

当前可按分类维度计算：

```text
分类重合分钟数 = min(计划分钟数, 实际分钟数)
分类可能分钟数 = max(计划分钟数, 实际分钟数)
时间掌控度 = 所有分类重合分钟数 / 所有分类可能分钟数
```

该指标适合粗略观察整体时间分布是否接近计划。后续可以加入时间轴重合度，提升精度。

## 9. 本地存储与数据可靠性

### 9.1 当前存储

使用 `localStorage`：

```text
daily_planner_entries_v1
```

### 9.2 风险

- 浏览器清理站点数据会丢失记录。
- 更换浏览器、设备或域名不会自动迁移。
- localStorage 容量有限。
- 没有数据版本迁移时，结构变化可能影响旧数据读取。

### 9.3 后续方案

第一阶段：

- 增加 JSON 导出。
- 增加 JSON 导入。
- 增加本地数据版本字段。
- 增加导入前备份提示。

第二阶段：

- 改为 IndexedDB。
- 支持本地快照。
- 支持 Cloudflare 云端同步选项。

## 10. Cloudflare 部署需求

### 10.1 Cloudflare Pages

当前应用适合先作为静态前端部署：

```text
Build command: npm run build
Build output directory: dist
Node.js version: 20
```

### 10.2 GitHub 集成

推荐流程：

1. 把项目提交到 GitHub 仓库。
2. 在 Cloudflare Pages 连接该仓库。
3. 设置构建命令和输出目录。
4. 每次 push 后自动构建。

### 10.3 后续云能力

如果后续需要跨设备同步，可以评估：

- Cloudflare Workers：提供 API。
- Cloudflare D1：存储结构化日记数据。
- Cloudflare KV：存储用户配置或轻量缓存。
- Cloudflare R2：保存导出的图片或备份文件。

第一版不引入云同步，避免增加账号、权限和数据安全复杂度。

## 11. 非功能需求

### 11.1 性能

- 首屏加载应保持轻量。
- 添加、编辑、删除时间块应即时响应。
- 保存本地数据不应造成明显卡顿。
- 导出长图时允许短暂等待，但需要明确显示导出中状态。

### 11.2 可用性

- 所有主要按钮有明确中文含义。
- 表单字段有清楚占位提示。
- 空状态能引导下一步操作。
- 删除、清空、导入覆盖等危险操作需要二次确认。

### 11.3 可访问性

- 按钮应使用真实 `button`。
- 输入框应关联可理解的 label。
- 颜色不能成为唯一信息来源。
- 移动端触控目标要足够大。

### 11.4 隐私

- 默认无账号。
- 默认不上传数据。
- 不加入分析、埋点、遥测或额外网络调用。
- 如后续加入云同步，需要明确说明数据存储位置和用户控制方式。

## 12. 验收标准

### 12.1 MVP 验收

- 用户可以完成一天的计划、实际、复盘记录。
- 刷新页面后数据仍存在。
- 可以切换历史日期并继续编辑。
- 可以从历史记录复用模板。
- 可以看到计划和实际的时长差异。
- 可以导出当天长图。
- 所有主要页面中文可读且无模板残留。
- `npm run build` 成功。

### 12.2 Cloudflare 验收

- GitHub 连接 Cloudflare Pages 后构建成功。
- 访问部署地址可以正常打开应用。
- 刷新页面无 404。
- 浏览器本地数据可以正常保存。
- 导出图片可正常下载。
